Lynch Rocket Lab · NASA GNEISS

12-node ground receiver network for ionospheric TEC

I designed and deployed a distributed Raspberry Pi receiver network to record 165 MHz beacon transmissions from the GNEISS sounding rockets. Measuring the signal's phase shift across 12 sites gives the total electron content (TEC) along each rocket-to-ground path, which lets the team map the structure of the ionosphere.

  • Cross-dipole antennas feeding SDRplay RSPduo receivers, demodulated in GNU Radio on Linux
  • Python automation for scheduled capture, file management, and data storage at every node
  • A fleet-control tool that starts and stops capture, pushes scripts, and pulls data from every station over SSH, from one terminal
  • A Raspberry Pi Zero 2 W test beacon: a GNU Radio flowgraph keys a 151.8 MHz transmission from a GPIO trigger and starts on boot under systemd, so the network can be checked end to end without a rocket
  • Field integration at NASA Wallops Flight Facility: instrumentation install, harness checks, vibe and spin testing, troubleshooting
  • Assembled and tested custom PCBs that capture the rocket instrumentation data

Dartmouth Student Rocketry in progress

STM32 avionics payload for a supersonic rocket

As a founding member and avionics team lead, I'm designing a custom STM32 flight computer PCB in KiCad that measures and logs the full flight and sends it to the ground. The firmware is already running on a NUCLEO-F446RE prototype.

  • Sensors: BNO085 IMU (orientation quaternion, acceleration, angular rate) and BMP388 barometer, both on SPI. Altitude is measured relative to a ground pressure averaged at boot.
  • Downlink: RFM95 LoRa radio at 915 MHz. Each packet is a packed 35-byte telemetry frame in fixed-point formats, with a compile-time size check that keeps the firmware and the Python ground decoder in sync.
  • Logging: SD card over 4-bit SDIO for post-flight analysis.
  • Graceful degradation: a status bitmask records which parts came up at boot, so a failed sensor doesn't take down the rest of the flight computer.
  • Next: a custom pitot tube for airspeed through the transonic regime, and moving everything onto the custom PCB.
  • Team lead: I set up the repo, the pull-request workflow, and a getting-started guide that takes new members from no coding experience to flashing the board.

TinyML word classifier with FIR filter bank and HDMI output

This is a spoken-word classifier that runs in programmable logic. Audio from the codec comes in over I²S and is converted to a mono AXI Stream. It passes through a bank of eight band-pass FIR filters, then into a custom Vitis HLS core that computes log-energy features and runs a 400→16→3 neural network. The predicted class (silence, word 1, or word 2) sets the color of an HDMI output.

The ML side (training, FIR design, and Q16 coefficient and weight export) lives in a Jupyter notebook. Its output files are the interface between the Python model and the hardware.

Engineering notes

Timing analysis

The routed design missed setup timing by −1.35 ns WNS on the 83.33 MHz fabric clock, while hold passed everywhere. I traced the critical path from the classifier's best_score register through argmax, the HDMI color logic, and into the debug ILA. About 88% of the delay is routing. The fixes are to drop the ILA from the release build and register class_out before the HDMI generator.

Open issue: Python ↔ HLS model mismatch

The hardware path works end to end, but the classifier only matches 7 of 9 reference vectors. The likely cause is a difference in feature scaling or quantization between the training notebook and the HLS implementation, not the RTL. Next I'd do a bit-exact comparison of each layer's outputs.

Integration fixes

  • Fixed AXI Stream width mismatches caused by the FIR Compiler's 40-bit full-resolution output.
  • Fixed a clock-domain crossing for the class result going into the pixel clock domain.

Real-time streaming audio DSP on Zynq

I built a stereo audio pipeline from the codec pins up, over three labs. Each lab added one layer and verified it in simulation before moving to hardware.

MCLK divided to BCLK/LRCLK in VHDL
24-bit
I²S samples at 48 kHz

selectable filters: LP, HP, BP, BS
What each stage does
  • I²S transmitter and receiver. Clock dividers (including a falling-edge divider for LRCLK), ODDR clock forwarding, and a 4-state FSM that shifts left and right channel data.
  • DDS tone generator. A phase-accumulator address counter steps through a sine lookup table in block RAM. It was later made programmable over AXI-Lite so the processor can set stereo test tones.
  • AXI Stream FIFO. A parameterized circular buffer with read/write pointers and an occupancy counter, wrapped with TVALID/TREADY handshaking.
  • DMA recorder. Streams codec audio into processor memory.
  • Selectable FIR stage. Sits between two FIFOs. A switch picks DDS tones or live codec audio as the input, which made the filter responses easy to check in hardware.
  • Codec setup. I²C configuration of the codec and clock-domain crossing between the audio and fabric clocks.

Ping-pong ball balancing platform with PID control in VHDL

A tilting platform that keeps a ping-pong ball centered. Two HC-SR04 ultrasonic sensors measure the ball's X and Y position, and two independent PID controllers drive hobby servos. Everything is written in VHDL with no soft processor: a clock generator, a sensor-receiver FSM that triggers the sensors and times the echo pulses, the PID datapaths, and PWM transmitters.

Tuning & debugging

I found the ultimate gain on a single axis and used it to set Ziegler–Nichols starting values. After smoothing the sensor path, those gains were too aggressive, so I hand-tuned to Kp=0.18, Ki=0.12, Kd=0.08.

The hardest bug was one that passing testbenches didn't catch. The PID output clamp only applied every other clock cycle, so when the ball left a sensor's view cone, a huge reading slipped through and pinned the servo at its limit. I fixed the clamp. The sensors still occasionally return out-of-range values, and filtering them added too much latency, so the next step is outlier rejection that adds no delay.

Joystick-controlled 2-axis marble maze game

A timed marble maze game driven by two stepper motors. It is written in bare-metal C on an STM32 with register-level GPIO setup and hand-written peripheral drivers. The joystick is read on two ADC channels, and the deflection sets how many steps each axis moves. A seven-segment display over I²C (HT16K33) shows menus, a countdown, and the time remaining. A TIM14 interrupt runs the 1-second game clock, and IR sensors at the start and finish detect the marble.

4-state
game FSM: ON → START → END → OFF
3
difficulty levels (step delay 10/5/1 ms, 60/45/30 s)
2

Firmware structure
  • A nested state machine handles debounced difficulty selection on the joystick button. The user button starts a 3-2-1-GO countdown on the display.
  • A dead zone around the joystick's center (ADC ≈ 2000–2100) prevents drift. Deflection beyond it is mapped linearly to a step count.
  • The timer ISR only sets a flag, and the main loop does the work. The countdown starts when the marble leaves the start sensor, and the LEDs flash in time with it.
  • Reaching the finish sensor lights the green LED and running out of time lights the red one. From there you can replay or power down.

Closed-loop position control: system ID to analog lead compensator

The goal was to make a motorized cart drive up to a wall and stop 7–9 cm away, quickly and with little overshoot. We identified the plant by filming the cart's step response and tracking it frame by frame, then linearized the IR distance sensor around the setpoint. From that model we designed a lead compensator with root-locus and frequency-domain methods and built it as an op-amp circuit.

4.64 → 0.92 s

The model

Plant: G(s) = 0.338 / (0.633s + 1), a first-order motor model with τ read at 63.2% of steady-state velocity and gain from the final value theorem.

Sensor: H(s) = 10.75 / s, which integrates velocity to position, with the gain linearized around 7 cm.

Compensator: Gc(s) = 1.58 (1 + 0.498s) / (1 + 0.068s), built with standard parts (C = 1 µF, Rs = 68 kΩ, R1 ≈ 430 kΩ, R2 = 680 kΩ). The single-stage inverting op amp flips the sign, so we swapped the motor leads to keep the feedback negative.

The ~1.5 cm residual error comes from motor stiction and the static-to-kinetic friction transition. Those are nonlinear disturbances that a Type-1 linear loop can't fully reject.

Analog heart-rate monitor with class-D audio output

The monitor takes the faint heart sound from a microphone, detects S1 (the "lub"), and outputs a 450 Hz beep and an LED flash on every beat. It plays a longer beep the first time it detects a heartbeat after being idle. There is no microcontroller. The signal chain is analog filtering, comparator pulse shaping, CMOS flip-flop logic, 555 timers, a Wien-bridge oscillator, and a class-D speaker driver. We modeled each block in LTspice before building it.

Signal chain & lessons

From the LTspice schematic

  • Idle and long-beep logic. Every detected beat retriggers a 3.3 s 555 timer, which a transistor discharges on each beat. When the timer expires, a D flip-flop latches an idle flag. AND/OR gates then send either the 400 ms "first beat" beep or the 200 ms normal beep to the oscillator gate.
  • Tone. An LF411 Wien-bridge oscillator with 1N4148 diode amplitude limiting in the feedback path. A complementary BJT switch gates it on and off.
  • Class-D stage. A PNP constant-current source charges a capacitor to make a linear ramp, which a comparator turns into PWM. Two LT1011 comparators, each behind a 4.7 kΩ / 1 nF delay, give break-before-make gate drive to a CMOS half-bridge. A 1 mH / 22 µF LC filter (≈1.07 kHz corner) and a DC-blocking capacitor feed the 8 Ω speaker.
  • Test stimulus. A recorded heartbeat played as a PWL source, 3 s on and 5 s off, which exercises the idle → long-beep path in simulation.

We verified each block against its simulation. The front end, comparator pulse shaping, beep timers, PWM carrier, and break-before-make gate drive all matched. Full integration was limited by two problems. The flip-flop sometimes clocked on the second heart-sound pulse, likely because the comparator's open-collector edges were slow. The Wien-bridge oscillator also became asymmetric right before the demo.

If I rebuilt it, I'd add Schmitt-trigger buffering on every clock input, check setup and hold margins, and plan the board layout from the start instead of adding breadboards as the design grew.
